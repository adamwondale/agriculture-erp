  id, actor_user_id, action, entity_type,

  before_snapshot (jsonb), after_snapshot

  ip_address, device_info, occurred_at
Non-negotiables:
audit_logs is insert-only. Enforce this with a DB-level
trigger or a restricted role that can't UPDATE/DELETE
that table — don't rely on application code discipline
alone, since the spec explicitly requires tamper-evident
logs.
Every table that matters for compliance gets
created_at, created_by, updated_at, updated_by.
Soft-delete (is_active/deactivated_at), never hard-
delete users — the spec requires historical
audits/signatures to survive offboarding permanently.
4. Backend Plan (C# / .NET 8 /
PostgreSQL)
Architecture: Clean Architecture / Vertical Slice — given this
service's complexity (auth + RBAC + approvals + audit),
don't just do a ﬂat CRUD API.
CoreAdmin.Api            -- controllers/minimal 
APIs, JWT middleware
CoreAdmin.Application     -- CQRS handlers 
(MediatR), validation (FluentValidation)
CoreAdmin.Domain          -- entities, domain 
rules (e.g. "no self-approval")
CoreAdmin.Infrastructure  -- EF Core + Npgsql, 
outbox pattern, event publishing
CoreAdmin.Contracts       -- shared DTOs/events 
package other services can reference
Key implementation decisions:
1. JWT design — embed sub, roles[], permissions[]
(or a permission-version hash if the token would get too
large), org_id, branch_scope_id,
active_delegation (if any). Short-lived access token
(10–15 min) + refresh token. Since permissions can
change mid-session (spec requires instant audit of
permission changes), keep a permissions_version
claim and have downstream services treat a version
mismatch as "re-fetch," not "trust blindly."
2. MFA — implement TOTP (Google Authenticator
compatible, via Otp.NET) for the mandatory roles, SMS
OTP as a fallback (routed through the future Integration
Gateway service — don't build your own SMS sending
here, just call out to it).
3. Authorization enforcement layer — build a single
IPermissionEvaluator that resolves: role permissions
→  user overrides →  ﬁeld-level rules →  branch/org
scope →  active delegation, in that order, and cache the
resolved set per user per short TTL (Redis). Every other
backend developer on your team should call this one
thing, never hand-roll if (user.Role == "Admin")
checks.
4. Self-approval prevention — this needs to be a domain
invariant, not a UI-only check. In the approval chain
execution logic, hard-reject if approver_user_id ==
submitter_user_id, regardless of what the frontend
sends.
5. Audit interceptor — use an EF Core SaveChanges
interceptor that automatically writes before/after JSON
snapshots for any tracked entity marked [Auditable],
rather than hand-writing audit calls in every handler.
Reduces the chance someone forgets to log a sensitive
change.
6. Event publishing — use the transactional outbox pattern
(EF Core table + background dispatcher) so
UserProvisioned, RoleAssigned,
OrganizationBranchCreated are never lost even if the
message broker is brieﬂy down. RabbitMQ or Kafka
both work; pick whichever the other 16 services will
standardize on.
7. Provisioning workﬂow — model the HR →  Assign →
Account Created →  Manager Approval →  Activation
ﬂow (Section 1.1 Q8) as an explicit state machine on
the users.status ﬁeld, not scattered boolean ﬂags.
Suggested backend build order (within this service):
1. Org hierarchy + branches CRUD
2. Users + password auth + JWT issuance
3. Roles + permissions + role_permissions
4. Permission evaluator + caching
5. User permission overrides + ﬁeld-level rules
6. MFA
7. Delegation
8. Approval chain conﬁg engine
9. Audit interceptor + audit query/export API
10. Outbox + event publishing

This is primarily an internal admin tool for Super Admin /
HR / IT — not the farmer/partner-facing portal (that's a later
service).
Core screens:

Org hierarchy builder (tree view: HQ →  Region →
Woreda →  Station)
User management (list, create via HR ﬂow, deactivate,
reassign)
Role management (Super-Admin-only: create role,
assign permission checkboxes, view matrix)
User permission override panel (grant/deny speciﬁc
permissions with mandatory reason ﬁeld)
Field-level permission matrix editor
Delegation setup (start/end date picker, scope, reason)
Approval chain conﬁguration (per transaction type, per
tier)
Audit log viewer with ﬁlters + CSV/signed-PDF export
Recommendation: Use a component library with a real
permission-matrix/tree-grid component (checkbox trees are
ﬁddly to hand-build well) — this will save the web team real
time on the role/permission screens speciﬁcally.
6. Mobile App Plan
Given the spec's emphasis on ﬁeld agronomists working
oﬄine, the mobile app's relationship to this service is
narrower than the web app's:
Login + MFA (SMS OTP path more likely than TOTP for
ﬁeld staff)
Silent token refresh + secure token storage
(Keychain/Keystore, not plain shared prefs)
Role/context display (if a user holds multiple roles, let
them see which one is active — don't build full role-
switching UI here unless a speciﬁc mobile use case
needs it)
Cache the resolved permission set locally after login so
the app can gate UI without a network call every screen
— refresh on permissions_version mismatch
No admin screens (role/permission editing) — that
stays on web
The mobile app's real complexity lives in the next service
(Farmer & Partner Management, oﬄine-ﬁrst), not this one —
keep Microservice 1's mobile footprint intentionally thin.
7. Cross-Cutting Checklist Before Calling
This Service "Done"
[ ] No service outside Core & Admin ever queries
users/branches tables directly (per your own
coupling discipline note) — all cross-service reads go
through published events or the GET
/users/{id}/permissions endpoint
[ ] Self-approval is blocked at the domain layer, tested
with an explicit unit test
[ ] Every permission change writes an audit row with
before/after snapshot + reason, veriﬁed with an
integration test
[ ] Delegations auto-expire (test with a background job +
clock manipulation, not just "insert an expired row and
check a query ﬁlters it")
[ ] MFA is enforced server-side for the mandatory role
list, not just hidden in the UI for those roles
[ ] JWTs are short-lived; refresh ﬂow tested for token
theft/replay scenarios
[ ] Audit log table has DB-level protection against
UPDATE/DELETE
[ ] Load test the permission evaluator — it will be called
by every request across 17 services either directly or via
cached claims, so it can't be the system's bottleneck
